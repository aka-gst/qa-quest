# QueQuest 2.x — long-game architecture

## Product goal

QueQuest is no longer designed as a short course-shaped campaign. The target is a game where a curious player can keep building for many sessions: move physical objects, diagnose systems, write real Python, train transparent models, assemble LLM wrappers and eventually design autonomous-but-bounded bots.

The target **20-hour shape is a design budget, not a measured playtime claim** until real playtests exist. The game should earn those hours through increasing system depth and recombination, not duplicated quizzes.

## Three layers of every major idea

1. **Story problem** — the player physically experiences why a concept is needed before seeing its formal name.
2. **Laboratory** — the player can isolate variables, rerun the mechanism and see internal state change.
3. **Contracts / sandbox** — the concept is recombined with earlier systems under new constraints, so mastery is behavioral rather than memorized.

A topic is not considered deep merely because it has more text. It needs observable state, a failure mode, a useful intervention and transfer into another problem.

## Current 2.0 play loops

### Main campaign

Eight game-first chapters remain the onboarding spine: manual work → automation → condition → queue → function → team routing → state → reliability → async factory.

### Systems campus

- 18 authored system-diagnosis contracts.
- Infinite deterministic shifts generated by seed.
- Visible input rate, service rate, burst, buffer, worker count, shared-write race, drops and collisions.
- XP once per solved seed; repeating a solved shift remains free practice.

### Python dock

24 real CPython/Pyodide behavior contracts:

- collections / strings / grouping / dedupe / batching / indexing;
- exceptions and resource boundaries;
- generators, dataclasses, context managers and ordering;
- dependency graphs, retry/backoff and JSON validation;
- typed actions and Protocol-based dependency inversion;
- asyncio gather/Queue/timeout/Semaphore;
- decorators/tool registries and LLM message boundaries.

### AI track

- transparent nearest-example classifier;
- hidden eval set and new labels;
- human reward that really changes action values;
- Model Workbench with a real one-layer softmax classifier;
- digits, letters and icon datasets;
- epochs, cross-entropy loss, weight heatmap, hidden noisy eval and data augmentation.

### LLM / agent track

- instruction vs data/context;
- structured action validation;
- tool allowlist;
- synthetic tool dispatcher;
- eval suite including hostile text inside untrusted data;
- provider-neutral Python Protocol wrapper.

### Progress

- local-first campus profile;
- XP and ranks;
- per-contract best results and lab mastery;
- unique award ledger for merge-safe XP;
- export/import JSON;
- versioned cloud/account sync transport contract, while login remains optional.

## Target 20-hour pacing budget

These numbers are targets for playtesting, not current measured completion times.

| Segment | Target | What should create the time |
| --- | ---: | --- |
| Main campaign | 3–5 h | movement, discovery, physical programming metaphors, story beats |
| Systems + Python campus | 5–7 h | 18 diagnosis contracts, 24 real code contracts, replay and debugging |
| Infinite system shifts | 2–∞ h | generated queue/burst/race configurations and optimization |
| AI foundations + workbench | 3–4 h | labels, eval, reward, epochs, weights, augmentation across datasets |
| LLM / agent engineering | 3–4 h | context, schema, tools, evals, provider adapters, later RAG/agents |
| Capstone | 2–4 h | build and harden a personal automation/AI factory |

The intended total crosses 20 hours only after the remaining 2.x vertical slices below are implemented and playtested.

## Deep vertical slices · implementation status

### 2.1 — Neural Foundry · IMPLEMENTED

Goal: show what a hidden layer adds rather than calling every classifier a neural network.

- perceptron → one linear layer → hidden layer;
- visible weights and activations;
- forward pass as moving signal;
- loss as a physical error gauge;
- backprop as responsibility flowing backward through edges;
- learning rate and instability;
- training / validation split;
- overfitting and early stopping;
- digits → letters → small noisy image families.

No heavyweight framework is required for the teaching model. A tiny deterministic implementation keeps every number visible. A later advanced mode may compare the transparent model with PyTorch when the runtime budget allows it.

### 2.2 — Retrieval Warehouse · IMPLEMENTED

Goal: make embeddings/RAG physically understandable before exposing provider SDKs.

- documents become crates/chunks;
- chunking changes retrieval granularity;
- embeddings become positions in a visible similarity space;
- query retrieves neighbors;
- bad chunking / missing context produces observable failure;
- citations are payload provenance, not decoration;
- context window has a capacity cost;
- prompt injection remains untrusted cargo, not system authority.

### 2.3 — Real provider adapters · OPTIONAL / NOT REQUIRED

Goal: let advanced players connect a real LLM without making accounts/API keys mandatory.

- a small `ModelClient` interface remains the game contract;
- adapters live behind explicit opt-in configuration;
- secrets stay outside save/export/profile;
- synthetic local Q-Mini remains the default so the game works offline;
- request/response traces can be inspected, redacted and evaluated;
- provider changes should not change lesson logic.

### 2.4 — Bot Forge · IMPLEMENTED

Goal: let the player build progressively more capable agents as systems, not personalities.

Modules:

- task intake;
- planner;
- state/memory;
- retrieval;
- tool registry;
- permission policy;
- executor;
- tests/evals;
- retry/timeout/budget;
- trace/log.

Missions should eventually include generating a tiny program, fixing a broken automation, assembling a small game rule-set and coordinating two bounded bots. The player sees every plan/tool/eval transition and can give feedback that changes later choices.

### 2.5 — Real-world Automation Lab / Pythonio bridge · IMPLEMENTED

Goal: transfer the factory language to useful personal automation.

- local file/folder tasks first;
- CSV/text/image metadata pipelines;
- safe HTTP/API simulation before live credentials;
- email/calendar connectors only with explicit user authorization;
- retry, idempotency, logging, checkpointing and dry-run modes;
- reusable blueprints the player can save and remix.

### 2.6 — Capstone: My AI Factory · IMPLEMENTED

The long-game finale should not be another boss. It is an open engineering brief with several valid architectures.

The player receives a noisy stream of tasks/files/messages and must build a bounded system that:

1. classifies input;
2. retrieves context when needed;
3. chooses from allowed tools;
4. performs actions through explicit interfaces;
5. survives retries/timeouts/duplicates;
6. logs enough to debug failures;
7. passes a hidden eval suite;
8. stays within a resource budget.

The visible factory becomes the architecture diagram. The final Python should be exportable as a readable project skeleton rather than a one-off answer.

## Account/backend boundary

Accounts are convenience, not gameplay authority.

- Game completion must remain possible without login.
- Local state is always readable immediately.
- Cloud sync stores the versioned progress envelope, not browser secrets or model API keys.
- Merge is monotonic: completed work is unioned, best scores are maxed and unique XP awards are merged by reason id.
- Auth transport can later be email, OAuth or a shared product account without changing the game profile schema.
- Server-side achievements/leaderboards, if ever added, should be derived from signed/validated events rather than trusting arbitrary imported JSON.

## Playtest questions for the next human pass

1. Where does a player stop understanding the physical metaphor and start merely following buttons?
2. Which contract takes much longer than its learning value justifies?
3. Does the infinite shift feel like optimization or like guessing hidden rules?
4. In Model Workbench, can a player explain the difference between epochs and better data after playing?
5. Does the LLM chapter make it clear that the model is replaceable and tools are separately authorized?
6. At what point does reading outweigh acting?
7. On a phone, are any important targets too small or any timelines unreadable?
8. Which system does the player voluntarily replay without being asked? That is the best candidate for deeper long-game content.


## 2.2 release note

The long-game core is now implemented through My AI Factory. The remaining provider-adapter item is intentionally optional: QueQuest keeps the synthetic local model as the default and does not require credentials. Two replay loops are available after authored progression: deterministic system shifts and deterministic AI Factory Trials. The 20-hour target remains a playtest budget, not a measured claim.


## 3.0 release note · SIMNET

The optional real-provider adapter is now preceded by a complete offline integration simulator. Five authored stations cover provider gateway boundaries, MCP host/client/server, Git evidence, service readiness/recovery and voice/vision privacy routing. Completion unlocks deterministic incident seeds for auth, allowlist, rate limit, timeout, streaming, schema, tool policy, readiness, duplicate side effects and secret leakage. Campus profile/schema is v3 with migration from v1/v2. Real provider credentials remain optional and outside save/export.
